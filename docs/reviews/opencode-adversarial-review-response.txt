### New or Unresolved Findings

**F1. CRITICAL — `_save_parse_results` drops parse runs on empty consolidated DataFrame**
- **File:** `src/analyzer/download.py:254-255`
- **Scenario:** When `consolidate_transactions()` returns an empty DataFrame (all documents had zero transactions after consolidation/date coercion), `ParsingError` is raised *after* `parse_runs` list was built but *before* `replace_transactions_for_docs` is called. Parse runs are lost — the documents are never recorded in `pdf_parse_runs`. On next re-parse, they'll be re-attempted indefinitely.
- **Severity:** Medium. Silent audit-trail gap. A downstream re-parse won't know these documents were already attempted.
- **Fix:** Write parse runs *before* raising `ParsingError`, or insert them in a separate `BEGIN/COMMIT` before the error.

**F2. HIGH — `_save_parse_results` includes zero-row parse runs in the batch sent to `replace_transactions_for_docs`**
- **File:** `src/analyzer/download.py:259-261`
- **Scenario:** `parse_runs` contains entries for *all* documents (both success and zero_rows). The batch transaction also deletes all existing rows for zero-row documents' doc_ids. But `consolidate_transactions` only returns rows for docs that *have* transactions. Zero-row docs are not in `df`, so their existing DB rows are deleted but nothing is inserted — the new code makes this atomic (the whole batch rolls back), but zero-row docs with existing rows cause a mass-delete of their transactions.
- **Wait — re-examining:** Actually, `df` comes from `consolidate_transactions(pdf_transactions, member_lookup)`. If a PDF yields zero transactions, it won't appear in `df`. The `doc_ids` in `replace_transactions_for_docs` come from `df["doc_id"].unique()`. So zero-row docs are *not* in the delete list. This is correct. **Retracted.**

**F3. HIGH — Log-return / simple-return mixing still present**
- **File:** `src/analyzer/signals/core.py:98` and `src/analyzer/signals/assembly.py:113-114`
- **Scenario:** `core.py:98` computes `r_decayed_ret[idx] = w_ret.sum() / w_sum` where `w_ret = log_ret * mid_d` — this is a **decay-weighted mean log return**. `assembly.py:113` then does `r_decayed_ret * 100` for `decayed_return_pct`. Log returns are not interpretable as percentage returns. A mean log return of 0.05 means `exp(0.05) ≈ 5.13%`, not 5%.
- **Severity:** Medium. All signal scores, rankings, and backtest results use this value. For small returns the error is negligible (~0.1%), but for volatile tickers over long horizons it can be meaningful.
- **Status:** This was identified in the Feb 2025 review. It is **not fixed**. The code comments in `assembly.py:57-59` acknowledge the prior double-division bug (Bug #1) but do not address the log→simple conversion.
- **Fix:** `(np.exp(r_decayed_ret) - 1) * 100` in `assembly.py:113`.

**F4. MEDIUM — `_TICKER_BLACKLIST` still blocks valid tickers including currency/OCR false positives**
- **File:** `src/analyzer/parsing/cells.py:12-24`
- **Scenario:** The blacklist contains `'O'` (Realty Income, a $60B REIT), `'X'` (US Steel), `'S'` (SentinelOne/SentinelOne). - **Fix:** Remove `O`, `X`, `S` (and potentially `A`, `P`, `E`) from `_TICKER_BLACKLIST`, or require `$TICKER` matches to end at a word boundary (`\b` or whitespace) and reject single-letter results unless whitelisted.
